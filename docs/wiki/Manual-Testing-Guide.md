# Manual Testing Guide

This repo ships 8 pre-baked fixture images in `samples/images/` (generated by
`samples/generate.py`, listed in `samples/manifest.json`) that exercise most signals and the
LOW_RISK/SUSPICIOUS bands, but three bands (REVIEW_RECOMMENDED, HIGH_RISK, INCONCLUSIVE) and a
couple of signal codes have no repo fixture — this guide gives a working recipe for each where one
exists, verified this session against the real running API.

## Using the existing fixtures

`samples/images/*.png|jpg`, each documented in `samples/manifest.json` with its
`expected_classification` and a `notes` field explaining what's wrong with it (or not). Running
`python samples/generate.py` (from `samples/`, inside the API's `uv` environment) regenerates the
full fixed set deterministically; `python samples/generate.py --check` verifies committed bytes
match without writing anything.

This script can only regenerate the EXISTING fixed fixture set — it has no CLI flags or
parameters to synthesize a new image with a different amount/date/CBU/CUIT, no EXIF-tag injection,
and no C2PA-manifest embedding capability at all (verified by reading its full source this
session).

## Testing each risk band manually

| Band | How to trigger it | Verified example |
| --- | --- | --- |
| LOW_RISK | Any clean fixture (`clean_valid_transfer.png` and 5 others — see manifest) | Confirmed via `samples/manifest.json`. |
| REVIEW_RECOMMENDED | No verified repo-local recipe today. A single moderate signal alone (e.g. `PROVENANCE_VALIDATION_FAILED`, weight 15) doesn't reach the 25-49 band; per the formula, combining two medium signals (e.g. `DATE_OUT_OF_BOUNDS` + `AMOUNT_DATE_CONTRADICTION`) should land here, but this hasn't been built and image-tested. | Not verified this session. |
| SUSPICIOUS | Upload `samples/images/invalid_cbu_check_digit.png` as-is | Verified this session: real API response, `risk_score: 60`, `classification: "SUSPICIOUS"` (previously documented in this repo as REVIEW_RECOMMENDED — corrected to match actual current behavior under ruleset `2026-09-06`). |
| HIGH_RISK | Generate a receipt-like image with an AI image generator that embeds a real C2PA (Content Credentials) manifest — Google Gemini/Imagen, OpenAI DALL-E 3, or Adobe Firefly all currently do this. Ask it for something like "a screenshot of a bank transfer confirmation receipt", download the image, upload it. | Verified this session with a real Gemini-generated image: `risk_score: 100`, `classification: "HIGH_RISK"`, `confidence_score: 100%`, triggering `AI_GENERATED_CLAIM_UNTRUSTED_SIGNER` (Gemini's signing CA isn't in the trust anchor list, but the claim itself validates cryptographically). |
| INCONCLUSIVE | Upload literally any photo that is NOT a transfer receipt (a selfie, a photo of a wall, a random screenshot with no financial text at all). | OCR completes but extracts zero of the 4 core fields, which is exactly the scenario the `scoring-confidence-calibration` change (see `openspec/changes/archive/` for that change's proposal) fixed to correctly return `INCONCLUSIVE` instead of a misleading `LOW_RISK`. |

If a manual test doesn't match the expected band, before assuming the analyzer is broken: check
`/version` reports the `ruleset_version`/`engine_version` you expect, and for anything
provenance-related, run `exiftool -a -G1 -s <file>` on the image yourself to confirm what
metadata/C2PA manifest (if any) is actually embedded — don't assume the AI generator embedded what
you think it did.

## Signals without a manual-testing recipe today

- `METADATA_EDITOR_SOFTWARE`: not from a synthetic fixture — take any real photo and edit/re-save
  it in Photoshop, GIMP, or Canva (these tools write a `Software`/`CreatorTool` EXIF/XMP tag
  `exiftool` will pick up); no repo tooling generates this today.
- `METADATA_AI_GENERATED_CLAIM`: **verified manually** — generate a fake receipt with Qwen
  (Tongyi) and upload it as-is. Qwen writes an XMP-TC260 `Aigc` tag (`{"Label":"1",...}`, China's
  mandatory AI-content-labeling standard) that survives a PNG round-trip; run
  `exiftool -json -n -- <file>` yourself first if you want to confirm the tag is present before
  uploading. No repo tooling generates this fixture today.
- `AMOUNT_DATE_CONTRADICTION`: requires OCR to find two disagreeing occurrences of the same field
  in one image (e.g. two different dates printed on the receipt) — `samples/generate.py` has no
  parameter for this; would need manual image editing or an AI generator prompted specifically for
  a receipt with an internal inconsistency, and is not verified/tested manually this session.
- A repeatable, locally-generated C2PA-manifest fixture (rather than relying on an external AI
  generator each time) and an EXIF-editor-tag fixture do not exist in this repo's tooling as of
  this change — worth a future `samples/generate.py` enhancement if this becomes a frequent
  manual-testing need.
